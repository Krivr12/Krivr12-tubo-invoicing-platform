Each processing attempt is one row with an `attemptNumber`. The row is created when the worker claims the invoice and completed when the result is recorded. Attempts are never overwritten or deleted. PostgreSQL treats NULLs as distinct in a unique index, so event rows without an attempt number do not collide.

## Relationships

- `companies` 1 → N `users`
- `companies` 1 → N `invoices`
- `invoices` 1 → N `invoice_items`
- `invoices` 1 → N `processing_logs`

## C1. Why the database is designed this way

- **Normalized tables.** Companies, users, invoices, items, and logs are separate tables, so each fact is stored once.
- **Company scoping.** Every invoice carries `companyId`, and the unique key and indexes start with it. Each company's queries and duplicate checks stay within that company.
- **Money as DECIMAL.** Amounts use `DECIMAL(12,2)`, not floating-point, so totals are exact.
- **Status as an enum.** The database rejects any status value outside the four allowed states.
- **Append-only logs.** `processing_logs` holds one row per event, so earlier errors are never overwritten.
- **Cascade deletes.** Deleting a parent removes its children, so no orphan rows remain.

## C2. Preventing duplicate invoices in the same company

The table has `UNIQUE (companyId, invoiceNumber)`. The database rejects a second row with the same company and invoice number, even if the application check is skipped or has a race. The API maps that error to `409 DUPLICATE_INVOICE`.

## C3. Two identical requests at the same time

Both requests try to insert `INV-10001` for ABC Corporation. The database lets one insert commit. The other insert fails on the unique constraint, and the API returns `409`. Only one invoice row exists. The guarantee comes from the unique constraint, not from a `findOne` check before the insert, because two requests can both pass that check at the same moment.

## Known gaps against the assessment

Attempt history, failure type, and the queue columns are now in the schema (migration `20261030090000_add_retry_queue_columns`). The remaining gaps are:

- **Naming and precision.** The steering rules call for `snake_case` columns and `numeric(14,2)` money. The current schema uses `camelCase` and `DECIMAL(12,2)`.
- **Company identifier.** Joining a company needs a `slug` column on `companies`, which the product rules require.
