## Layer rules (backend)

Each module is under `backend/src/modules/<name>/`. Requests flow in one direction: `routes → controller → service → Prisma`.

- **`routes.ts`** maps paths to controller functions and attaches middleware. No logic.
- **`controller.ts`** parses the request with the module's Zod schemas, calls the service, and sends the response. No business rules and no Prisma calls.
- **`schema.ts`** holds the Zod schemas for body, query, and params.
- **`service.ts`** holds business rules: totals, status transitions, and retry eligibility. It is the only file in a module that calls Prisma for request-driven work. Every company-data query takes `companyId`.
- **`processor.ts`** holds the worker logic: claiming due invoices, calling the government service, and recording each attempt. It is the only code that calls the government service.
- **`middleware/`** holds cross-module code: authentication, error handling, and rate limiting. `AppError` lives in `errorHandler.ts`.
- **`config/`** loads and validates environment variables.

## Frontend rules

- Organize by feature under `frontend/src/features/`. Each feature folder holds its own pages, hooks, and components.
- Shared UI pieces (loading, empty, and error states, and the status badge) live in `frontend/src/components/`.
- Put the API client wrapper and general helpers in `frontend/src/lib/`.

## Migrations

- Change the schema only in `backend/prisma/schema.prisma`, then run `prisma migrate dev`. Review the generated SQL in `backend/prisma/migrations/` and commit it with the code that depends on it.
- Do not change the schema by hand in the database, in a GUI tool, or with `psql`.
- Do not edit a migration that has already been applied. Add a new migration instead.
